# 給餌SQL 2本の整合性確認

本番未適用・mainへのpush保留。最新の仕様は「最新投稿が就寝系なら寝姿・給餌不可、awake系なら起きて給餌可能」。一度就寝したら当日ずっと禁止する方式は採用しない。

## 状態と投稿履歴

`supabase/reactions-by-post.sql` の `oyasumi_submit_post_v2` と `test-fixtures/reactions-base.sql` の旧RPCは、投稿変更をINSERTで保存する。最新は `event_order` 順。v2は同じ選択・intentの60秒重複抑制と1分10件制限を維持する。フロントの取得履歴は100件、一覧表示は3時間で消えるため、その一覧だけを睡眠判定の根拠にしない。

旧／v2の投稿RPCもguard内で更新する。最新行を削除した後、60秒以内に古い行と同じ内容を再投稿すると、旧判定は古い行を返すだけで状態トリガーを発火させなかった。保存済み状態の順序が残存行より新しい場合は重複扱いにせず、新規INSERTにする。通常の60秒重複抑制と1分10件制限は維持する。日付と作成時刻は本人ロック後の同じ時刻から計算し、待機中の06:00またぎもそろえる。

新しい非公開テーブル `oyasumi_cat_post_states` に、ユーザー・06:00区切りの日付ごとの最新投稿順序／choice／時刻を保存する。投稿トリガーが旧RPC・v2 RPC・UPDATE・DELETEを捕捉する。投稿行への外部キーは置かず、履歴削除のカスケードで状態が消えないようにした。

| 操作 | 猫と給餌 |
| --- | --- |
| 最新投稿が sleep / try-sleep / early-sleep | 寝姿・給餌不可 |
| その後に awake / awake系intent を投稿 | 起きて給餌可能（残回数は増えない） |
| 画面移動・再訪・3時間経過・深夜0時 | 最新状態を維持 |
| 最新投稿の削除 | 保存済み状態を維持。古い投稿へ巻き戻さない |
| 古い履歴行の更新・削除 | 最新状態を変更しない |
| 最新行のchoice更新 | 新しいchoiceに変更 |
| 投稿トランザクションのROLLBACK | 状態保存も同時に取り消す |
| 翌06:00 | 通常状態。前日の行は削除せず判定対象外にする |

既存の投稿・給餌・おやつ行は変更しない。初回は残っている投稿から日別の最新状態を埋める。**移行前に削除済みの最新投稿は復元できない**ため、その日の完全な状態を復元する必要がある場合はバックアップ等が必要。初回適用は06:00のリセット後、投稿受付を再開する前が最も明確。

フロントは同じstatus RPCの `sleepStateVersion=1` と `catState` をホーム・ごはん画面・給餌可否に使う。投稿保存成功直後も、確定したchoiceで同じ値を更新する。旧サーバーでは従来の最新投稿判定を使用する。画面構成・文言・CSS・画像・他のSNS機能は変更しない。

## ロック・権限・既存制限

- 投稿RPCは既存の本人ロック `hashtextextended(user_id::text,0)` を維持し、時刻・日付を取得後に計算する。給餌とおやつRPCは **本人ロック → careロック** の順。時刻は両方のロック取得後に読む。
- `BEFORE STATEMENT` トリガーが投稿のINSERT / UPDATE / DELETEで、行ロック取得より先に認証ユーザーの本人ロックを取る。行トリガーだけで本人ロックを取ると、先に行をロックする削除と、本人ロック後に投稿行を読むリアクションで逆転するため、文単位で取得する。
- 正常なクライアント操作は本人の投稿に限定する既存RLS／所有権チェックが前提。他人の投稿を変更する管理者バッチやトリガーを無効化する保守操作は、書き込み停止中に行う。
- 新しい状態テーブルはRLS有効・クライアント用ポリシーなし。PUBLIC / anon / authenticatedの直接権限を取り消す。内部関数・トリガー関数もクライアントから実行不可。
- 公開care RPCは引き続き認証必須・空search_pathのSECURITY DEFINER。就寝中の給餌は `P0042` で拒否し、行を挿入しない。
- 旧／v2投稿RPCも空search_pathのSECURITY DEFINER・認証チェックを維持し、EXECUTEをauthenticatedだけに限定する。本番の既存ACLと比較してから適用する。
- 給餌は06:00〜12:00と12:00〜翌06:00の各1回。おやつは1日2匹・同じ相手に1回。既存の主キー、ON CONFLICT、careロックを維持する。awakeへの変更や履歴削除で残回数を回復させない。おやつの既存仕様には就寝制限を追加しない。

## 2本の適用順序と再適用

1. 前提は既存 `cat-care.sql` のテーブル、旧投稿RPC、`reactions-by-post.sql` のv2投稿RPCとpost_intent、06:00版 `oyasumi_night_date_at`。既存v2環境へ旧 `cat-care.sql` を再適用しない。投稿RPCを置き換える移行はguardより前に完了させる。
2. `cat-care-two-windows.sql` を適用する。既存行・元の日付／時刻を保持してv2の列と主キーを整える。
3. `cat-care-sleep-guard.sql` を適用する。v2列・主キー・投稿RPC・post_intent・日付関数がそろっていなければ `55000` で変更前に中止する。日付関数の05:59:59.999／06:00の返り値も検査し、旧境界なら変更前に中止する。投稿書き込みをロックしてバックフィルとトリガー設置の間の取りこぼしを防ぐ。
4. 2本に含まれる4つのcare関数の定義を一致させた。guard後にwindowsだけを再適用しても、保存済み状態・トリガー・就寝拒否は維持する。guard再適用のバックフィルは、保存済み順序より新しい投稿だけを採用し、削除済みの最新状態を古い行で上書きしない。

初回の2本の間は状態保護がまだ完成していないため、投稿・給餌の受付を止めたまま続けて適用する。すでにv2が適用済みで列・制約が一致する場合は、事前確認後guardだけでも更新できる。各ファイルは1トランザクションで適用する。

後から `reactions-by-post.sql` 等で投稿RPC本文を再作成すると、削除後重複判定の修正が上書きされる。その場合は受付停止中にguardを最後に再適用する。windows→guardの2本の再適用では、この上書きは起こらない。

## 本番RPCとの差分確認と適用手順

本番DBへの接続・SQL実行は今回行っていない。比較の基準はリポジトリと、2026-10-11確認済みとの注記がある投稿RPC fixture。本番の現在の定義と一致すると断定しない。特に `oyasumi_delete_post` の本番定義はローカル資料にないため、テストでは所有者チェック付きDELETEの契約を模擬している。

承認後、管理者が [cat-care-state-inspect.sql](cat-care-state-inspect.sql) を実行して結果を保存する。この読み取りSQLは関数全文／MD5・所有者・EXECUTE権限、列・主キー・RLS・ポリシー・投稿トリガー、共通列の行数と集計チェックサムを返す。保存RPCは呼ばない。

照合する差分:

| 対象 | 予定する変更 |
| --- | --- |
| care status / status_at | 非公開の最新状態を返す。sleepStateVersion・catState・mealSleepingを追加 |
| give_cat_meal | 本人→careロック。保存済み最新状態がsleepならP0042 |
| give_cat_treat | 本人→careロックに統一。回数・対象判定は維持 |
| submit_post / submit_post_v2 | 削除済みの新しい状態があれば古い行を重複として返さない。ロック後の同じ時刻でnight_dateとcreated_atを決定。認証専用ACL |
| delete_post / reaction RPC本文 | 変更しない。既存権限・所有権・ロック順を事前確認 |
| oyasumi_posts | 2個のトリガー追加。既存の列・行・トリガーを維持 |
| 新規状態テーブル・4内部関数 | 追加／更新。クライアントの直接利用を拒否 |

確認事項は、投稿順序が一意かつ単調なevent_orderであること、投稿の直接書き込みRLSが本人限定であること、既存RPCにcare→本人という逆順ロックや未把握の別ロックがないこと、既存トリガーとの競合がないこと。特に削除RPCがDELETE前にSELECT FOR UPDATE等を行う場合、本人ロックより先に行ロックを取っていないか確認する。想定外の差分があれば適用せず再レビューする。

状態の日付判定は投稿の `created_at` を使い、投稿と給餌の時刻はロック後に読み直す。投稿RPCの変更はローカル資料の本文が基準のため、本番に追加の検査や列設定等がないか全文を照合する。未把握の変更があれば上書きせず統合して再検証する。

適用承認後の手順:

1. 対象プロジェクトを確認し、バックアップと適用前inspection結果を保存。書き込み停止中に行数／チェックサムを控える。
2. 上記順序でSQLを適用。本番の初回と同じ構成をステージングで検証してから本番へ進む。
3. inspectionを再実行。既存共通列の値と変更対象外RPC本文／権限が維持され、状態テーブルが非公開、トリガーが各1個、care関数・旧／v2投稿関数が新版であることを照合する。
4. 許可された検証アカウントでsleep→拒否→awake→給餌、再訪、削除後維持、二重操作、おやつ制限を確認する。これは本番書き込みの別途承認範囲内だけで実施する。
5. SQL適用結果の確認後に、今回のフロント変更のmain pushを別途承認範囲で行う。

旧guardへの巻き戻しは削除耐性を失うため、障害時はまず給餌受付を止めて修正する。追加テーブルを削除して状態を失う操作は行わない。
